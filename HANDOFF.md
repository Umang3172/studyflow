# Studyflow Handoff (for the coding model)

**State (2026-10-08):** planning finished; no application code exists yet. The next step is **M0 (spikes + scaffold)** in [PLAN.md §16](PLAN.md#16-milestones-and-acceptance-criteria). You should not need the planning transcript; it is archived in the README appendix.

## What we are building

An "exam sprint coach" for one student per browser: streaming tutor chat (Llama 3.3 on Workers AI), persistent memory, a syllabus → study-plan Workflow with student approval, scheduled reminders and a daily check-in, live synced state, and optional push-to-talk dictation. The full scope and non-goals are in PLAN.md §1.

## Non-negotiables

- Model: `@cf/meta/llama-3.3-70b-instruct-fp8-fast` (24k context). **Always set `maxOutputTokens`** (the model default is 256).
- The client never chooses its agent instance. The Worker maps the signed `sf_session` cookie to `getAgentByName(env.StudyAgent, userId)`. Never expose `routeAgentRequest` to public traffic.
- `validateStateChange` rejects every non-server write. Mutations go through zod-validated `@callable` methods.
- zod at every trust boundary (callables, tool inputs, workflow params, LLM JSON).
- Reminders: compute UTC from the student's IANA timezone and use `schedule(Date, …)`. Re-arm the daily check-in from its own callback.
- No secrets in git (`.dev.vars` is ignored). Never handle the user's Cloudflare or GitHub credentials; ask them to run `wrangler login` and `wrangler secret put`.
- Ask the user before deviating from Pages (decision D4), adding dependencies beyond PLAN.md §12, or installing agent plugins or hooks.
- Keep README.md current (see "Maintaining README" below).

## Coding guidance

Adapted from Ponytail's "smallest complete change" rules ([source](https://github.com/DietrichGebert/ponytail/blob/main/AGENTS.md), MIT):

1. Before editing, list everything the change must reach (callers, tests, fixtures, config, exports) and what it could break or expose. That list is the scope; extra features are not.
2. Pick the first option that fully works: skip what nobody asked for → reuse what is in the repo → use the platform (Agents SDK, Web APIs, `Intl`) → use an installed dependency → write one readable line → only then write the minimum new code.
3. No speculative abstractions, options, wrappers or "for later" code. Keep the layout in PLAN.md §13.
4. Never cut validation at trust boundaries, data-loss error handling, security or accessibility.
5. Non-trivial logic (planner, time, auth, budget, parsers) ships with a small test. Trivial wiring does not need one.
6. A deliberate shortcut gets a `// ponytail: <limit>, upgrade when <condition>` comment.
7. Comments explain *why* in one line. Finish with a note of what you skipped or did not verify.

Cloudflare and SDK gotchas found during planning:

- Extend `agents/tsconfig`. **Never** set `experimentalDecorators` (it silently breaks `@callable()`). Add the `agents/vite` plugin wherever Vite 8 or Vitest compiles decorator code.
- Use Vitest **4.1.x** with `@cloudflare/vitest-plugin@1.3.7`. `@cloudflare/vitest-pool-workers` is deprecated, and Vitest 5 is not supported yet.
- AI SDK 7 docs show both `stepCountIs` and `isStepCount`; use whichever the installed `ai` exports.
- The `cloudflare/agents-starter` template is behind (`agents@0.17`, `ai@6`). Scaffold fresh with the pins in PLAN.md §12 instead of copying it.
- Workflows: deterministic step names, side effects only inside `step.do`, step results < 1 MiB, start workflows only from name-addressed agents, and keep class names in bundles (`keep_names`).
- Agent state broadcasts to every client, so keep it small and put collections and secrets (for example push subscriptions) in SQL.
- The rate-limit binding window is 10 or 60 seconds only; limits are per location and approximate. Do not key on IP alone except for session minting.
- `pause`/`resume`/`terminate`/`restart` for Workflows do not work under `wrangler dev`; test them deployed.

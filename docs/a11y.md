# Accessibility audit

Date: 2026-10-08. Target: WCAG 2.2 level AA. Automated checks run in CI (`apps/web/e2e/a11y.spec.ts`).

## What was checked

| Check | How | Result |
| --- | --- | --- |
| Automated rules (WCAG 2.0/2.1/2.2 A and AA, plus axe best practices) | axe-core 4.13.0 through `@axe-core/playwright`, on onboarding, empty chat, chat with messages and a tool result, plan form, plan review (with the Mermaid chart), active plan, Memory, Settings and Today | 0 violations after fixes |
| Colour schemes | Every screen above in light and in dark (`prefers-color-scheme`) | 0 violations |
| Viewports | Desktop Chrome (1280 wide) and Pixel 7 (412 wide, touch) | 0 violations |
| Keyboard only | Tab from the top of the page reaches the message box with a visible 2 px focus ring on every stop; typing and Enter send; focus stays in the message box while the reply streams in; Memory and Settings open with Enter and Space | Pass |
| Reflow (WCAG 1.4.10) | 320 px wide: no horizontal page scrolling on onboarding, chat, Today, Plan, Memory and Settings | Pass |
| Reduced motion | `prefers-reduced-motion: reduce` makes transitions effectively instant | Pass |
| Text size | 200% root font size keeps the message box and Send button visible and usable | Pass |
| Live regions | The transcript is `role="log"` with `aria-live="polite"` and `aria-busy` while streaming; toasts sit in a polite status region | Pass (structure only) |

## Findings and fixes

| # | Finding | Impact | Fix |
| --- | --- | --- | --- |
| 1 | Primary buttons picked up the generic button hover background, so the hovered "pressed" tab (and Approve buttons) showed white text on light grey. Axe flagged it on every screen where the pointer rested on one. Reverting the fix makes the test fail again. | serious (colour contrast) | `.btn-primary` now sets its own hover background (`styles.css`) |
| 2 | The study-session list and the timeline chart scroll but could not be reached by keyboard | serious | Both are focusable (`tabIndex=0`) with an accessible name; the chat transcript got the same so it can be scrolled with the keyboard |
| 3 | The onboarding screen had no `main` landmark and its content sat outside any landmark | moderate | Wrapped in `<main>`; the loading screens use `<main>` too |
| 4 | The transcript could be read token by token by screen readers during streaming | not detectable by axe | `aria-busy` while streaming |

Axe samples colours mid-transition, so the scan waits for CSS animations to finish before measuring (otherwise a button that just became pressed is reported with half-faded colours).

## Not covered (needs a person)

Automated tools find roughly a third of accessibility problems. Still to do by hand before a public launch:

- **Screen readers:** VoiceOver (Safari, iOS) and NVDA (Firefox or Chrome). In particular listen to a streamed reply, a reminder toast, the plan review screen and the tool-approval card.
- **The timeline chart** is an image with a short label; the session list under it carries the same information as text. Confirm that is acceptable to your users.
- Voice dictation and "Read aloud" use browser APIs; test them with the OS voice and speech tools.
- Windows High Contrast / forced-colours mode, browser zoom beyond 200%, and colour-vision simulations.
- Touch target size on small phones (buttons are about 32 px tall; WCAG 2.2 AA requires 24 px, which they meet; 44 px is the stricter AAA guidance).
